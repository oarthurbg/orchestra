---
description: (Maestro) Map an existing codebase into docs/codebase-map.md: how it is built, its conventions, where the risk is, and its history
---

You are the maestro (skill `orchestra:maestro`). Write or refresh the codebase map that planners and principals read before they plan. Run it once when you take stock of a project already under way, and again only when the owner asks.

1. **Gather the facts, at no token cost.** From the main checkout, run:
   `mkdir -p .orchestra && node "${CLAUDE_PLUGIN_ROOT}/codemap/codemap.mjs" --root . > .orchestra/codemap.json`
   It reads the tracked files and the last 12 months of git history: folders, entry points, which folders import which, tests, the most changed files and the files with the most fix commits. It records no author names. On an error (not a git repository, no commits), tell the owner and stop.

2. **Turn them into the map.** Dispatch the `explorer` with this brief: read `.orchestra/codemap.json`, then only what you need to explain it (the entry points, the README, the "Project settings" of `CLAUDE.md`, one or two files of the most imported folders). Return the text of `docs/codebase-map.md`, at most 120 lines, with these sections and nothing else:
   - **How it is built:** the stack, the entry points, how a request or command flows through the main folders.
   - **Parts:** one line per main folder: what it holds and what it depends on (from `imports` and `mostImported`).
   - **Conventions:** naming, file layout, how tests are written and run, anything a new task must follow. Only what the code shows.
   - **Risk:** the files under `history.risk`, each with its fix count and whether a test covers it, plus the most imported folders, where a change reaches furthest. One line each: why it is risky.
   - **History:** age, total commits, activity by month in one line, the most changed files.
   - A last line: `Generated by /orchestra:codemap on <date> from <commit>. Facts in .orchestra/codemap.json.`
   No names of people, no credentials, nothing the project's CLAUDE.md marks as confidential.

3. **Commit it through a docs PR.** Dispatch the `mechanic` to write that text to `docs/codebase-map.md` unchanged, commit it on a short branch from the integration branch and open a PR into it. Merge it as you merge any docs PR.

4. **Tell the owner** in a few lines: the risk files, the parts the change reaches furthest from, and the PR. From now on the planner tags tasks that change those files as `sensitive`.

The map is a snapshot: it does not refresh itself. When the code has moved a lot (a few waves, a big rewrite), offer to run this again.
